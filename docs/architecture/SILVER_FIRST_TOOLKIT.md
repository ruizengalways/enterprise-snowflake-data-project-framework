# Silver-first Project Toolkit

## One sentence

Ingestion preserves source evidence in Bronze, explicit domain-owned Snowflake SQL establishes trusted Silver, and dbt starts from Silver to build Gold and Semantic models.

## Why

The previous implementation hid ordinary project behavior behind shared dbt macros and custom materializations. A domain engineer had to understand the Framework repository before answering basic questions such as how an SCD2 table handles replay or late-arriving data.

This architecture optimizes for local reasoning instead:

```text
Source -> BRONZE -> silver_processing/<dataset> -> SILVER -> dbt -> GOLD -> SEMANTIC
```

A reviewer can understand a Silver pipeline from files committed in the same domain repository.

## Bronze

Bronze is ingestion-owned, source-faithful evidence. It can contain multiple versions of a business key and can retain delivery duplicates when the ingestion mechanism cannot safely remove them without losing evidence. Connector checkpoints remain connector-owned.

## Silver

Silver is the correctness boundary. Stateful or procedural work belongs here:

- deterministic deduplication;
- SCD1 current-state maintenance;
- SCD2 authoritative history;
- tombstone delete/reinsert behavior;
- replay/idempotency;
- late-arrival correction;
- source-event ordering.

The implementation is normal Snowflake SQL in `silver_processing/<dataset>/`. Stored procedures, Streams or Tasks are allowed when they make stateful behavior clearer; they are not generated by a runtime metadata engine.

## dbt

dbt starts from trusted Silver sources. It owns warehouse modeling work: facts, dimensions, marts, business joins, KPI calculations, aggregations, tests, lineage, documentation and semantic models.

The toolkit is not installed as a dbt package. There is no shared custom materialization.

## Reuse model

Reuse happens through reference patterns and scaffolding:

```text
esf scaffold scd2 vehicle_status --raw-contract contracts/raw/vehicle_status.yml
```

The command copies files once. The generated SQL is then committed to the domain repository and can diverge when the domain genuinely requires different logic.

Runtime upgrades to the toolkit therefore cannot silently alter existing data behavior.

## Control plane

Shared run/reset/audit/quality state can remain in `PLATFORM_CONTROL`, exposed through guarded domain-scoped procedures and views. That is an operational contract, not a reason to hide Silver SQL behind dbt macros.
